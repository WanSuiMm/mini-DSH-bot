# OpenAI-Compatible Protocol Boundary

The implementation uses [DeepSeek's `deepseek-recipe` at commit `935817c66f5d6e64838f419692545f06787e485f`](https://github.com/deepseek-ai/deepseek-recipe/tree/935817c66f5d6e64838f419692545f06787e485f) as a protocol-design reference. The upstream project provides Rust libraries and Python bindings that convert Messages, Chat Completions, and Responses requests into a shared conversation model, render DeepSeek V4/V4.1 prompts, and parse model output. Its caller supplies inference, tool execution, and HTTP transport.

`OpenAICompatibleAdapter` is an independent TypeScript adapter for the Chat Completions HTTP format. It is not a direct integration or code port of `deepseek-recipe`. It validates the internal conversation before creating wire messages: assistant tool-call IDs are unique, every tool result matches one pending call, all calls are resolved before the next non-tool message, and tool arguments must serialize as JSON. Response tool calls require a nonempty ID and function name plus parseable JSON arguments. Malformed conversations or responses fail before the agent loop can dispatch parsed tool calls.

The adapter sends only worker-authorized tool definitions. Actual tool execution remains in `AgentLoop` and the configured `ToolRuntime`/`ToolRegistry`. Existing provider selection, model IDs, token budgets, and default request fields are unchanged. For complete non-streaming JSON responses only, a missing `finish_reason` retains legacy compatibility: parsed calls imply `tool_call`, otherwise the response is treated as `stop`. Explicit `length` without calls remains a truncation signal for `AgentLoop`; `length` with calls, `content_filter`, `stop` with calls, and unknown finish reasons fail closed.

Streaming is opt-in by passing `streaming` to `OpenAICompatibleAdapter` or setting `MICRO_DSH_STREAMING=1` in the service. Without the option the existing non-streaming request remains in effect. Opt-in requests set `stream_options.include_usage=true`; configured endpoints must support this standard Chat Completions option. A rejected request is returned as an error without retrying it with different accounting behavior. The stream reader incrementally decodes UTF-8 and SSE data, accepts multiline `data:` events, assembles indexed fragmented function-call IDs, names, and arguments, and returns calls only after the finish reason, `[DONE]`, and clean event-delimited EOF are all present. A terminal `choices: []` usage chunk is accepted after the finish event when it has complete, consistent token counts; response ID/model metadata must stay stable when present. If usage is omitted, the existing local-estimate accounting fallback applies. The reader rejects truncated, filtered, malformed, invalid/incomplete-index, oversized, or incomplete tool-call responses. Reasoning fields are ignored; they are not returned as text or included in tool arguments. Service defaults are 4 MiB response bytes, 8,192 data events, and 32 calls; hard ceilings are 32 MiB, 100,000 events, and 32 calls. `MICRO_DSH_STREAM_MAX_RESPONSE_BYTES`, `MICRO_DSH_STREAM_MAX_EVENTS`, and `MICRO_DSH_STREAM_MAX_TOOL_CALLS` can lower those caps.

This independent TypeScript boundary does not integrate the upstream Rust/Python library, implement Messages or Responses APIs, render DeepSeek V4/V4.1 prompts, or decode native token IDs. Tests use mocked HTTP responses and make no model/API calls. See `tests/adapters.test.mjs` and `tests/model-config.test.mjs` for focused CPU checks.
